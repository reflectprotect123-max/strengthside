## Findings

### Critical

#### C-1 — The `strengthLoad` unit change silently freezes the strength autopilot for any athlete with pre-v60 history

**Files:** `apps/mobile/prototype/hybrid-app/recovery-engine.js` (`sessionTrainingLoad`, `deliveryLoadLedger`), `apps/mobile/prototype/hybrid-app/load-headline.js` (`sumChannel`).

**What the plan asked.** S6: replace the `tonnage/50` stub with the engine's `sessionLoad`. R3: soften load-headline copy only. Both were implemented as written.

**What the code does.** `summary.strengthLoad` changed meaning in commit `b5a0787`: it used to be `tonnage / 50` (order 100), it is now raw `tonnageKg` (order 5000). Both `recovery-engine.js` and `load-headline.js` read `summary.strengthLoad` across the athlete's whole stored history, and neither can tell which scale a given row is in. `sessionTrainingLoad` compensates with a flat `strength / 50`, which is correct for post-v60 rows and divides pre-v60 rows a second time.

I ran the mixed-history case against the shipped module — three prior weeks of legacy rows (`strengthLoad: 100`) plus a current week of new rows (`strengthLoad: 5000`), green check-in, no other signals:

```
mixed-scale ledger -> { delivered: 315, training: 315, budget: 21, ratio: 15, elevated: true }
posture gate      -> caution [ 'checkin_build', 'delivery_load_elevated' ] cap 52
```

A green day is downgraded to `caution`. `RecoveryEngine.blocksProgressionBumps` returns true for `caution`, so `StrengthAdapter.applySilentProgression` converts every `progress` decision to `hold` (except a performance override). `capacityHint` also drops from 85 to 52. This persists until the 3-week budget window has rolled entirely onto new-scale data.

The same mixed history pins the load headline at its ceiling:

```
mixed headline -> { headline: 32.2, strengthDisplay: 21, conditioningDisplay: 11.2, rawStrength: 15100 }
```

`strengthDisplay: 21` is the hard cap in `normalizeDisplay`.

**Why this is Critical rather than cosmetic.** The product contract is *invisible brains*. There is no surface that would tell the athlete their autopilot has stopped bumping, and no smoke covers a mixed-scale history — `recovery-engine.smoke.mjs` builds five sessions all in the new scale, so the ratio stays sane and the case never fires.

**Concrete fix.** Derive the strength channel from `summary.tonnage`, which is raw kilograms and has been written unchanged in every version of `finishSession` (verified at `9fd2555` and `9fd2555~1`), so it is the one scale-stable field:

```js
function sessionTrainingLoad(s) {
  if (!s || s.status !== 'completed') return 0;
  var sum = s.summary || {};
  var tonnage = num(sum.tonnage);
  var strength = tonnage > 0 ? tonnage / 50 : num(sum.strengthLoad);
  var cond = num(sum.conditioningLoad);
  if (strength > 0 || cond > 0) return strength + cond;
  return num(sum.totalLoad);
}
```

Apply the same substitution in `load-headline.js` — have `sumChannel` read `summary.tonnage` for the strength channel instead of `summary.strengthLoad`. Then add a mixed-scale fixture to `recovery-engine.smoke.mjs` and `load-headline.smoke.mjs` (legacy rows where `strengthLoad === tonnage / 50`, new rows where `strengthLoad === tonnage`) asserting the gate stays `ok` and `strengthDisplay` stays below the 21 cap.

### Important

#### I-1 — An existing autopilot load hint silently overrides an explicit `%WM` prescription

**File:** `apps/mobile/prototype/hybrid-app/strength-adapter.js` (`applyLoadHintsToExercise`).

**What the plan asked.** S4 Step 1: "for each exercise with `loadExpr`, call `resolveExerciseLoad`; if resolved, prefill row `weight`".

**What the code does.** The hint is applied before the expression, and `fillBlankRowWeights` only writes into rows whose weight is `''` or `null`. Once the hint has filled a row it is no longer blank, so the `loadExpr` branch below it is a no-op for that row:

```js
var hint = ensureStrengthState(state).loadHints[exerciseId];
if (hint && hint.loadKg) fillBlankRowWeights(ex, hint.loadKg);
if (ex.loadExpr) { /* resolved value can never land — rows are already filled */ }
```

Reproduced against the shipped adapter with working max 100 kg, `loadExpr` 70 %, and an existing hint of 120 kg:

```
row weight with BOTH hint(120) and 70%WM(70) -> 120
```

The athlete authored 70 % of working max on the lift sheet and gets 120 kg. `strength-session-start-load.smoke.mjs` cannot catch this: every fixture in it has `loadHints: {}`.

**Concrete fix.** Resolve the explicit prescription first and fall back to the hint only when it is unresolved:

```js
function applyLoadHintsToExercise(state, ex, asOfDate) {
  if (!ex) return;
  var exerciseId = ex.exerciseId || ex.id;
  if (!exerciseId) return;
  if (ex.loadExpr) {
    var resolved = resolveExerciseLoad(state, ex, asOfDate);
    if (resolved && resolved.loadKg != null) { fillBlankRowWeights(ex, resolved.loadKg); return; }
  }
  var hint = ensureStrengthState(state).loadHints[exerciseId];
  if (hint && hint.loadKg) fillBlankRowWeights(ex, hint.loadKg);
}
```

Add a fixture to `strength-session-start-load.smoke.mjs` with a populated `loadHints` entry alongside a `loadExpr`, asserting the `%WM` value wins.

### Minor

#### M-1 — `completeConditioning` does not call `applyConAdapt` (currently unreachable, but a live trap)

**File:** `apps/mobile/prototype/hybrid-app/index.html`.

You asked specifically whether the hybrid train path was missed. The answer is nuanced: the call is genuinely absent from `completeConditioning`, but that function cannot currently be reached.

`train()` short-circuits before it ever renders a conditioning card:

```js
function train(){let x=activeSession();if(!x)return go('home');let t=current();
  if(t&&t.kind==='conditioning'){renderSimpleCondLog();return} ... }
```

So the later `if(t.kind==='conditioning')b+=conditioningTask(t);` in the same function is dead, and with it `conditioningTask`, `intervalTask`, the two "Complete block" buttons, and `completeConditioning`. `refreshCondLogOrTrain()` routes conditioning back to `renderSimpleCondLog()` as well. The two reachable finish paths — `completeSimpleCond` and `confirmCondFinished` — both call `EngineAdapter.applyConAdapt(S, EngineAdapter.condResultFromTask(t, S))` before `save()`.

Two consequences. `tickCondZoneSeconds` also early-returns unless `simpleCondLog`, which is consistent with the routing. And if anyone ever re-enables the multi-task conditioning card, `conAdapt` stops firing with no test failure, because `engine-adapt.smoke.mjs` only asserts `html.includes('applyConAdapt')` — one occurrence anywhere satisfies it.

**Concrete fix.** Either delete the unreachable block (`conditioningTask`, `intervalTask`, `completeConditioning`, and the `if(t.kind==='conditioning')b+=conditioningTask(t)` line), or add the `applyConAdapt` call to `completeConditioning` and strengthen the smoke to count occurrences rather than test for presence.

#### M-2 — `mergeSnapshots` throws `ReferenceError: num is not defined` outside the browser

**File:** `apps/mobile/prototype/hybrid-app/strength-sync.js`.

`num` is used at the PR-merge branch but never defined in the module. Every sibling adapter (`strength-adapter.js`, `load-headline.js`, `recovery-engine.js`, `coordinator-adapter.js`, `engine-adapter.js`) declares its own local `num`; this one relies on the global that `index.html` happens to define. Reproduced:

```
THROWS: ReferenceError num is not defined
```

In the browser it resolves against `window.num`, so shipped behaviour is fine. It is pre-existing (`90ba8b7`, before this plan), but S7 is the task that extended this function, and `strength-sync.smoke.mjs` cannot catch it — its fixture has an empty local `prEvents` array, so the `!cur` short-circuit fires before `num` is ever evaluated.

**Concrete fix.** Add the standard local `function num(v){var n=Number(v);return Number.isFinite(n)?n:0;}` to the IIFE, and give the smoke a fixture where both sides hold a PR for the same `exerciseId:repCount`.

#### M-4 — `capacityHint` can be `null` while the band is known

**File:** `apps/mobile/prototype/hybrid-app/recovery-engine.js`.

R2 asks for a 0–100 number whenever the band is known. `capacityHint(checkin, gate)` returns `null` on `!checkin`, so:

```
checkinComplete true, checkin null -> { band: 'build', gate: 'ok', capacityHint: null }
```

Unreachable from current callers — `recoveryInputForPosture` computes `checkinComplete: !!(c && checkinComplete(c))`, and `coordinator-adapter.js` does the same — so this is a contract gap, not a live bug. (The realised range is 20–100 rather than 0–100, which is inside the stated bound and looks deliberate.)

**Concrete fix.** Give `capacityHint` a checkin-less baseline derived from `gate` alone, or assert the invariant in `recoveryPosture` (`band !== 'insufficient_data'` implies `capacityHint != null`) and cover it in the smoke.

## Verdict

**Not "nothing missed."** Three things were missed, in priority order:

1. **Critical — C-1.** The `strengthLoad` unit change from `tonnage/50` to raw `tonnageKg` is read across mixed-scale history by `recovery-engine.js` and `load-headline.js`. For any athlete with pre-v60 sessions, the delivery ledger reads a ~15× ratio, downgrades green days to `caution`, and silently holds every strength autopilot bump for roughly three weeks, while the load headline sits pinned at its 21 cap. Invisible by design, uncovered by any smoke. Fix by deriving the strength channel from the scale-stable `summary.tonnage`.
2. **Important — I-1.** S4 is functionally wrong when a lift already has an autopilot load hint: the hint fills the rows first, so the athlete's explicit `%WM` prescription is discarded. Fix the ordering in `applyLoadHintsToExercise` and add a fixture with a non-empty `loadHints`.
3. **Important — I-2.** N3's smoke re-implements `buildDailyRecords`' mapping instead of calling the function it was exported to test, so Phase 2's single behavioural claim is unverified. Call the real function.

Eight Minor items follow, led by the unreachable `completeConditioning` path that omits `applyConAdapt` (M-1) and the `num` ReferenceError latent in `mergeSnapshots` (M-2).
